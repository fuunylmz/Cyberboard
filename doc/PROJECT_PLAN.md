# Cyberboard 项目完整规划方案

## 1. 文档定位

Cyberboard 的目标是构建一个与 V2Board 类似的控制面板产品，用于管理用户、套餐、订阅、节点、流量和内核配置，并兼容 sing-box 等运行内核。

本方案只定义产品边界、架构、协议、数据模型、技术栈和实施路线，不包含具体实现代码。项目采用前后端分离架构，后端和节点 Agent 使用 Rust，前端使用 TypeScript。

### 1.1 推荐结论

- 后端：Rust + Axum + Tokio。
- 节点 Agent：Rust，独立二进制程序。
- 前端：Vue 3 + TypeScript + Vite。
- 数据库：PostgreSQL。
- 缓存、限流和异步任务：Redis。
- 前端 API：REST + OpenAPI。
- 控制面与 Agent：Agent 主动出站的 gRPC 长连接或长轮询 + mTLS；控制面不主动连接节点。
- 配置完整性：Ed25519 签名。
- 初期部署：Docker Compose。
- 初期架构：模块化单体 API + Worker + Agent，不直接拆成大量微服务。
- 初期内核：优先实现 sing-box，之后增加 Xray、Clash Meta 等适配器。

## 2. 产品目标与边界

### 2.1 产品目标

1. 提供统一的用户、套餐、订阅、节点和流量管理能力。
2. 通过统一配置模型生成不同内核所需的配置。
3. 通过节点 Agent 安全地分发配置和管理内核进程。
4. 支持面板生成面向不同客户端的订阅内容。
5. 支持配置版本、发布、回滚、审计和节点健康监控。
6. 保证在节点数量增加时，控制面可以水平扩展。

### 2.2 首期不包含的内容

- 自研代理协议或替代 sing-box/Xray 的内核。
- 控制面直接登录节点执行任意 Shell 命令。
- 第一阶段同时支持所有客户端和所有内核版本。
- 第一阶段拆分成大量独立微服务。
- 把支付渠道、短信、邮件等第三方服务写死在核心领域模型中。

### 2.3 使用角色

| 角色 | 主要权限 |
|---|---|
| 系统管理员 | 全局配置、用户、节点、套餐、审计和运维 |
| 运营人员 | 用户、订单、订阅、套餐和通知 |
| 节点运维 | 节点注册、核心版本、配置发布和健康状态 |
| 普通用户 | 查看套餐、订阅、流量、设备和账户设置 |
| 代理商（可选） | 管理自己范围内的用户和订单 |

代理商和多租户属于可选能力，建议在领域模型中预留 `tenant_id`，但首期可以只启用一个默认租户。

## 3. 总体架构

```text
                         +----------------------+
                         | Vue 3 Web Frontend   |
                         | Admin / User Portal  |
                         +----------+-----------+
                                    |
                              HTTPS REST API
                                    |
+-------------------+     +--------v---------+      +----------------+
| CDN / Reverse     |---->| Rust API Service |----->| PostgreSQL     |
| Proxy / TLS        |     +--------+---------+      +----------------+
+-------------------+              |
                                   v
                            +------+------+
                            | Redis       |
                            | Cache/Queue |
                            +------+------+
                                   |
                            +------v------+
                            | Rust Worker |
                            +------+------+
                                   |
                    Agent outbound gRPC + mTLS
                                   |
              +--------------------+--------------------+
              |                                         |
       +------v-------+                           +-----v--------+
       | Rust Agent   |                           | Rust Agent   |
       | Node A       |                           | Node B       |
       +------+-------+                           +-----+--------+
              |                                         |
       +------v-------+                           +-----v--------+
       | sing-box     |                           | sing-box     |
       +--------------+                           +--------------+
```

### 3.1 控制面

控制面负责业务状态和期望状态：

- 用户、身份认证、角色和权限。
- 套餐、订阅、订单和到期策略。
- 节点、节点分组、内核版本和能力标签。
- 统一配置模型、模板和配置版本。
- 订阅生成与访问令牌。
- 流量额度、用量聚合和封禁策略。
- 节点健康状态和运维事件。
- 审计、通知和后台任务。

### 3.2 节点 Agent

Agent 是运行在节点机器上的最小权限服务，负责：

1. 首次注册和凭证轮换。
2. 周期性心跳和能力上报。
3. 拉取控制面发布的配置清单。
4. 校验配置签名、版本和目标节点。
5. 在本地进行配置语法检查。
6. 启动、平滑重载和停止指定内核进程。
7. 保留最近可用配置，失败时自动回滚。
8. 聚合流量和健康指标并批量上报。
9. 下载经过签名的 Agent 或内核升级包。

Agent 不接受任意命令，不保存管理员密码，也不直接访问控制面的业务数据库。Agent 只主动向控制面建立出站连接，节点不需要开放控制面入站管理端口。

### 3.3 前后端分离

- 前端编译为静态资源，可以部署到 CDN、Nginx 或对象存储。
- 后端只提供 JSON API、订阅接口和实时状态接口。
- 前端不接触节点私钥、数据库凭证或 Agent 管理凭证。
- API 使用 OpenAPI 生成类型定义和客户端代码，减少前后端字段漂移。
- 管理后台和用户中心可以共用组件库，但权限和路由分开。

## 4. 仓库与部署单元规划

建议使用一个 Cargo Workspace 管理 Rust 后端和 Agent，前端单独使用 Node.js 工作区：

```text
cyberboard/
├── apps/
│   ├── api/                  # HTTP API、认证、业务编排
│   ├── worker/               # 异步任务和统计聚合
│   └── agent/                # 节点 Agent
├── crates/
│   ├── domain/               # 领域实体、值对象、错误模型
│   ├── database/             # SQLx、迁移、事务封装
│   ├── auth/                 # 密码、Token、RBAC
│   ├── subscription/         # 订阅和配置编译
│   ├── config-compiler/      # 统一配置模型和编译流程
│   ├── core-adapter/         # 内核适配器 Trait 和实现
│   ├── agent-protocol/       # gRPC 协议和消息模型
│   └── observability/        # tracing、metrics、健康检查
├── frontend/
│   ├── admin/                # 管理后台
│   ├── portal/               # 用户中心
│   └── packages/             # 共享类型、组件和 API Client
├── deploy/
│   ├── docker-compose.yml
│   ├── migrations/
│   └── examples/
├── docs/
└── doc/
    └── PROJECT_PLAN.md
```

API、Worker 和 Agent 可以先共用部分 crate，但编译成独立进程，便于后续分别扩容。

## 5. 技术栈与工程约定

### 5.1 Rust 后端

- Web 框架：Axum。
- 异步运行时：Tokio。
- 数据库访问：SQLx + PostgreSQL。
- 序列化：Serde。
- 参数校验：validator 或领域层自定义校验。
- 日志和追踪：tracing、tracing-subscriber。
- API 文档：utoipa 或兼容 OpenAPI 的方案。
- gRPC：tonic。
- HTTP 客户端：reqwest。
- 密码哈希：Argon2id。
- 加密签名：Ed25519、成熟的 Rust 密码学库。

原则：业务层不得直接依赖 Axum 类型；领域逻辑放在 crate 中，HTTP 层只负责协议转换和鉴权上下文注入。

### 5.2 前端

- Vue 3 + TypeScript + Vite。
- 路由：Vue Router。
- 状态管理：Pinia。
- 数据请求：基于 OpenAPI 生成的客户端，或封装的 typed client。
- UI：Naive UI、Arco Design 或 Element Plus，最终只选一个。
- 图表：Apache ECharts。
- 测试：Vitest + Playwright。

前端不重复实现业务规则。额度、价格、权限和订阅有效期都以服务端判定为准。

### 5.3 Web 前端完整规划

#### 5.3.1 前端产品面

前端分为两个独立入口，共用基础组件、API Client 和设计令牌：

```text
frontend/
├── admin/       # 管理后台
├── portal/      # 用户中心
└── packages/
    ├── api-client/
    ├── ui/
    ├── auth/
    ├── types/
    └── utils/
```

管理后台面向管理员、运营人员和节点运维；用户中心面向普通用户。两个入口可以分别部署，也可以由同一个反向代理按路径分发。

#### 5.3.2 管理后台页面规划

| 模块 | 页面 | 主要能力 |
|---|---|---|
| 总览 | Dashboard | 用户数、在线节点、流量、异常和待处理任务 |
| 用户 | 用户列表、用户详情、设备 | 搜索、筛选、状态、订阅、额度、登录记录 |
| 套餐 | 套餐列表、套餐编辑 | 价格、有效期、流量、并发、节点组和上下架 |
| 订阅 | 订阅列表、订阅详情 | 生效、续期、暂停、撤销和令牌轮换 |
| 节点 | 节点列表、节点详情、节点分组 | 心跳、资源、内核版本、配置版本和维护状态 |
| 配置 | 模板、草稿、版本、发布记录 | 校验、差异、发布、灰度、回滚和失败原因 |
| 流量 | 实时用量、用户排行、节点用量 | 时间范围、分组、趋势、导出和异常峰值 |
| 订单 | 订单列表、支付事件 | 状态、金额、回调、退款和人工处理记录 |
| 系统 | 管理员、角色、设置、审计 | RBAC、系统参数、密钥状态和操作日志 |
| 运维 | 任务、告警、Agent 发布 | 任务重试、告警确认、版本灰度和升级结果 |

列表页优先支持服务端分页、筛选、排序、批量操作和导出；详情页使用选项卡组织概要、配置、用量、事件和审计信息。高风险操作必须使用确认弹窗，并展示影响范围和不可逆后果。

#### 5.3.3 用户中心页面规划

| 页面 | 主要能力 |
|---|---|
| 首页 | 当前套餐、到期时间、剩余流量、最近设备和节点状态 |
| 套餐 | 可购买套餐、权益比较和续费入口 |
| 我的订阅 | 订阅状态、订阅令牌、配置下载和令牌轮换 |
| 使用量 | 日、周、月用量趋势和额度预测 |
| 设备 | 已使用设备、最近活动和撤销设备 |
| 订单 | 订单、支付状态、发票或凭证信息 |
| 安全设置 | 修改密码、会话管理、二次认证预留 |
| 帮助 | 客户端配置说明、常见错误和服务状态 |

订阅令牌只在明确的用户操作后展示或复制；页面不得把完整令牌写入普通日志、埋点或错误上报。

#### 5.3.4 路由和权限

前端路由分为公开路由、用户路由和管理路由：

```text
/login
/portal/*
/admin/*
/subscribe/:token
```

路由守卫只负责快速判断登录状态，最终权限必须由后端校验。后端返回当前用户的角色和权限集合，前端根据权限隐藏菜单、禁用操作并处理无权限页面；不能把隐藏按钮当作安全措施。

管理后台建议使用资源和动作表达权限，例如：

```text
user:read
user:write
node:read
node:deploy
config:publish
config:rollback
audit:read
```

#### 5.3.5 前端状态管理

状态分为三层：

1. **会话状态**：当前用户、Token、权限、租户和当前工作空间。
2. **服务端状态**：用户、节点、配置、流量、订单等 API 数据，使用查询缓存、失效和重新拉取管理。
3. **页面状态**：筛选条件、弹窗、表单草稿、选中的行和图表时间范围。

不要把所有 API 数据复制到全局 Store。服务端数据应以查询缓存为事实来源，写操作成功后按资源粒度失效缓存，避免出现多个页面状态不一致。

#### 5.3.6 API Client 和错误处理

- 从 OpenAPI 生成 TypeScript 类型和请求方法。
- 统一处理 401、403、409、422、429 和 5xx。
- 401 只允许一次 Refresh Token 重试，失败后清理会话并回到登录页。
- 403 显示无权限页面，不自动重试。
- 409 显示资源版本冲突，并提供重新加载或查看差异的入口。
- 422 将字段错误绑定到表单，不只显示通用 Toast。
- 每次请求携带或回传 `request_id`，错误页面允许复制该 ID。
- 破坏性写操作使用 `Idempotency-Key`，避免重复点击造成重复发布或重复订单。

#### 5.3.7 实时数据和任务反馈

节点状态、配置发布和 Agent 升级使用 SSE 或 WebSocket 推送；API 轮询作为降级方案。前端应显示任务状态机，而不是只显示一个无限旋转的 Loading：

```text
pending -> running -> succeeded
                    -> failed
                    -> rolled_back
```

配置发布页面必须显示目标节点、当前版本、目标版本、校验结果、执行进度、失败原因和回滚结果。用户离开页面后，任务仍由后端继续执行，重新进入页面时从服务端恢复状态。

#### 5.3.8 设计系统和交互规范

- 使用统一的颜色、字体、间距、圆角、阴影和层级 Token。
- 管理后台以信息密度和可扫描性为优先，不使用营销式大面积装饰。
- 危险操作使用明确的危险色、二次确认和操作结果反馈。
- 节点在线、离线、维护、异常使用文字和颜色双重表达，避免只依赖颜色。
- 表格提供空状态、加载状态、错误状态和无权限状态。
- 表单提供字段级校验、提交中状态、失败恢复和未保存提示。
- 配置 JSON 或差异使用等宽字体、折叠和语法高亮，并支持复制。
- 图表提供时间范围、单位、时区和数据更新时间。
- 桌面端优先适配 1280px 以上；用户中心兼容移动端；管理后台移动端提供基本查看和处理能力。

#### 5.3.9 国际化、时区和可访问性

- 所有用户可见文本进入 i18n 资源，不在组件中散落硬编码。
- 服务端统一保存 UTC，前端根据用户设置展示时区。
- 金额、日期、流量和百分比使用本地化格式化工具。
- 表单、弹窗、表格和图表支持键盘操作和焦点管理。
- 颜色对比度满足可读性要求，状态不只通过颜色传达。
- 错误信息使用用户可理解的文案，同时保留可检索的错误码。

#### 5.3.10 性能规划

- 管理后台和用户中心分开构建，按路由懒加载。
- 大表格使用服务端分页，必要时使用虚拟滚动。
- 图表只请求当前时间范围和聚合粒度，禁止一次加载全部流量明细。
- 订阅和节点列表使用缓存、去重请求和请求取消。
- 静态资源启用压缩、长期缓存和内容哈希。
- 首屏只加载当前路由需要的组件，复杂配置编辑器按需加载。
- 通过 Lighthouse、Playwright 和浏览器性能指标持续检查首屏时间、交互延迟和错误率。

#### 5.3.11 前端安全

- 优先使用 HttpOnly、Secure、SameSite Cookie 保存会话；若采用 Bearer Token，必须限制存储位置和有效期。
- 不把长期 Token 放入 URL、普通 localStorage 或分析事件。
- 富文本、配置预览和错误详情必须进行输出转义，防止 XSS。
- 订阅链接页面设置合理的缓存策略，避免令牌进入代理或浏览器历史记录。
- 管理端启用 CSP、CSRF 防护、严格 CORS 和安全响应头。
- 前端依赖启用锁文件、漏洞扫描和构建产物审计。

#### 5.3.12 前端测试与交付

测试分层：

- 单元测试：格式化、权限判断、状态转换、表单校验和 API 错误映射。
- 组件测试：表格、弹窗、表单、配置差异和图表空状态。
- 页面测试：登录、用户、节点、配置发布、回滚和订阅下载。
- E2E 测试：管理员和普通用户各自的完整主流程。
- 视觉回归：关键页面的桌面和移动端截图基线。
- 可访问性检查：键盘导航、焦点、语义标签和颜色对比度。

CI 流程建议为：

```text
format -> typecheck -> lint -> unit test -> build
       -> component test -> E2E -> visual regression
```

前端构建产物使用内容哈希，部署后保留上一版本以支持快速回滚。API 发生破坏性变更时，先发布兼容后端，再发布前端，避免前后端同时升级导致页面不可用。

## 6. 领域模块

### 6.1 身份与权限

- 用户注册、登录、退出和设备管理。
- 管理员登录和强制二次认证预留。
- Access Token 短期有效，Refresh Token 轮换并可撤销。
- RBAC：角色、权限、资源范围。
- 代理商或租户隔离时，所有业务查询强制带 `tenant_id`。

### 6.2 用户与订阅

- 用户状态：正常、暂停、封禁、已删除。
- 订阅状态：待生效、生效、过期、取消、超额暂停。
- 套餐包含：有效期、流量额度、并发限制、设备限制、可用节点组。
- 订阅链接使用独立随机令牌，不暴露用户主登录凭证。
- 订阅令牌支持轮换、撤销和访问审计。

### 6.3 节点管理

- 节点名称、地域、地址、端口和标签。
- Agent 版本、内核版本、平台、架构和能力。
- 节点分组、权重、维护状态和发布状态。
- 最后心跳、CPU、内存、磁盘、核心状态和当前配置版本。
- 节点凭证可撤销、可轮换，不能明文展示。

### 6.4 配置管理

- 统一配置模型。
- 配置模板、变量和环境覆盖。
- 配置草稿、校验、发布、回滚。
- 配置版本与内核版本绑定。
- 配置变更必须记录操作者、差异、目标节点和结果。

### 6.5 流量统计

- Agent 本地按时间桶聚合。
- 控制面按用户、节点、套餐和时间维度汇总。
- 统计上报具备幂等键，重复上报不会重复计费。
- 明细数据和汇总数据分层保存，按保留策略归档。
- 额度判断优先使用缓存，最终以数据库事务结果为准。

### 6.6 订单与支付

订单和支付应通过 Provider 接口隔离：

```text
PaymentProvider
├── create_order()
├── query_order()
├── verify_callback()
└── refund()
```

支付回调必须验签、幂等处理并记录原始事件。支付模块可以在 MVP 后加入，但订单状态模型应提前设计。

## 7. 统一配置模型与内核适配

### 7.1 设计原则

系统内部保存“意图”和“能力”，不把某一个内核的原始配置作为唯一数据源。生成的原始配置是可重建的发布产物。

Endpoint、Inbound、Transport、TLS 和 Credential 使用规范化字段建模，并由内核能力矩阵控制可用字段；确实无法统一的字段放入带版本和校验规则的扩展区。密码、私钥和其他秘密字段通过独立的密文引用保存，不直接进入普通配置 JSON。

每个配置版本至少包含：

```text
config_revision_id
schema_version
core_type
core_version_range
node_id
content_hash
signature
created_by
created_at
```

### 7.2 适配器接口

```text
CoreAdapter
├── capabilities()
├── validate(model)
├── render_server_config(model, node)
├── render_client_subscription(model, user, format)
├── inspect_usage(report)
└── compatibility(core_version, schema_version)
```

进程启动、重载和回滚属于 Agent Runtime 层，不应全部塞进配置渲染器。这样可以让配置编译和节点执行分别测试。

### 7.3 兼容策略

1. 首期锁定一个经过测试的 sing-box 精确构建版本，并维护版本兼容矩阵。
2. 内核版本升级先进入兼容性测试，再允许发布到生产节点。
3. 每个适配器维护 JSON/YAML golden fixtures。
4. 配置生成后必须经过 schema 校验和内核原生检查。
5. 新版本配置失败时自动保留上一份可用配置。
6. 客户端订阅格式和服务端内核配置分开建模。
7. 后续通过新 Adapter 增加 Xray、Clash Meta 或其他核心。

## 8. Agent 与控制面协议

### 8.1 注册流程

1. 管理员在面板创建节点，获得一次性注册信息。
2. 注册信息只保存哈希，短时有效、单次使用、绑定目标 `node_id`，并进行限流和防重放校验。
3. Agent 使用注册信息提交公钥或 CSR，控制面校验节点归属。
4. 控制面签发带有 `ca_id`、`key_id` 和有效期的 Agent mTLS 证书。
5. Agent 保存本地凭证，后续只使用出站 mTLS gRPC 通信。
6. 一次性注册信息立即失效；证书、CA 和签名密钥支持轮换与吊销。

### 8.2 心跳内容

```text
agent_id
node_id
agent_version
core_versions
platform
architecture
current_config_revision
core_state
resource_metrics
timestamp
nonce
```

### 8.3 配置发布流程

1. 管理员提交配置草稿。
2. 控制面校验领域模型和内核兼容性。
3. 编译器生成目标节点配置。
4. 独立 signer 或受限 Worker 计算内容哈希并进行 Ed25519 签名。签名 envelope 至少包含 `key_id`、`content_hash`、`target_node`、`generation`、`issued_at` 和 `expires_at`，签名输入使用明确的 canonical bytes。
5. Agent 拉取或收到新版本通知。
6. Agent 校验签名、信任根、节点 ID、generation、版本号和有效期，拒绝过期或乱序配置。
7. Agent 写入临时文件并执行本地配置检查。
8. 检查通过后原子替换并平滑重载内核。
9. 重载失败则回滚上一份配置并上报结果。发布使用 generation/CAS 保证幂等，结果包含旧/新 hash、阶段、错误码和重试次数。

### 8.4 流量上报

- Agent 按分钟或五分钟生成使用量桶。
- 每个批次带有 `agent_id`、时间范围、序列号和幂等键。
- 控制面确认后，Agent 才删除本地待上报数据。
- 网络中断时本地持久化并重试，限制本地队列大小。
- 控制面保存追加式 `usage_events` 或 `ingest_receipts`，记录批次序列、来源、校验和去重结果，再异步汇总到 `usage_buckets`。
- Redis 只用于缓存和可靠队列，不作为计费事实来源。

关键约束：

- 用量接收记录追加写入，结算汇总通过可重放的异步任务生成。

## 10. API 规划

### 10.1 API 约定

- 路径版本化，例如 `/api/v1`。
- 使用统一错误结构：错误码、消息、字段错误和请求 ID。
- 分页接口使用游标优先，后台简单列表可使用页码。
- 所有写操作返回资源版本或事件 ID。
- 支持 `Idempotency-Key` 的接口：支付、配置发布、流量上报和节点注册。
- 所有响应带 `request_id`，便于排查。

### 10.2 用户端接口示例

```text
POST   /api/v1/auth/login
POST   /api/v1/auth/refresh
POST   /api/v1/auth/logout
GET    /api/v1/me
GET    /api/v1/me/subscriptions
POST   /api/v1/subscription-tokens/rotate
GET    /subscribe/{token}
GET    /api/v1/me/usage
```

订阅接口必须使用 TLS，响应设置 `Cache-Control: no-store` 和 `Referrer-Policy: no-referrer`，日志不得记录完整令牌或完整 URL，并按令牌版本失效缓存。接口需要独立限流，令牌撤销后立即失效。

### 10.3 管理端接口示例

```text
GET    /api/v1/admin/users
POST   /api/v1/admin/users
PATCH  /api/v1/admin/users/{id}
GET    /api/v1/admin/plans
GET    /api/v1/admin/nodes
POST   /api/v1/admin/nodes
POST   /api/v1/admin/nodes/{id}/rotate-credential
POST   /api/v1/admin/config-revisions/{id}/publish
POST   /api/v1/admin/config-deployments/{id}/rollback
GET    /api/v1/admin/audit-logs
```

### 10.4 Agent 接口

Agent 接口不与普通用户 API 共用权限模型，使用 Agent 主动建立的独立 gRPC 服务。协议需要定义最大消息、deadline、断线重连抖动、协议版本和 feature negotiation：

```text
RegisterAgent
Heartbeat
GetDesiredState
ReportApplyResult
ReportUsage
GetReleaseManifest
ReportUpgradeResult
```

## 11. 安全方案

### 11.1 身份与凭证

- 密码使用 Argon2id，并设置合理的内存和迭代参数。
- Access Token 短期有效，Refresh Token 轮换并支持撤销。
- 管理员和普通用户使用不同的会话策略。
- 节点凭证可单独撤销和轮换。
- 订阅令牌与登录 Token 完全分离。

### 11.2 配置和密钥

- 配置发布包使用 Ed25519 签名，签名密钥不由普通 API 进程直接读取。
- 私钥放在 KMS、Vault 或受保护的密钥服务中。
- 数据库中的敏感字段使用应用层加密。
- Agent 只接收目标节点所需的配置。
- 日志禁止输出密码、Token、私钥和完整订阅令牌。

### 11.3 权限与审计

- API 中间件完成认证，领域服务完成资源级授权。
- 租户、代理商和节点组权限必须在服务端强制过滤。
- 配置发布、回滚、封禁、凭证轮换和支付回调全部写入审计日志。
- 审计记录不可被普通管理员删除或修改。

### 11.4 Agent 安全

- 使用独立系统用户运行。
- 仅访问配置目录、内核进程和必要的指标接口。
- 禁止远程任意命令执行。
- 升级包校验签名和哈希。
- 配置文件使用原子写入，避免进程读取半成品。
- 保留有限数量的历史配置，避免磁盘被耗尽。
- Agent 使用固定可执行文件白名单调用内核检查和启动流程，不通过 Shell 拼接命令。
- Agent 由 systemd 等服务管理器以独立系统用户运行；低端口能力通过最小化的 `CAP_NET_BIND_SERVICE` 或内核自身权限配置解决。
- Agent 更新使用双槽或双目录、签名 manifest、健康检查、可撤销发布和自动回滚，限制安装目录和版本回退范围。

## 12. 部署与运维

### 12.1 MVP 部署

```text

├── frontend static files
├── Rust API
└── subscription endpoint

Rust Worker
PostgreSQL
Redis
Object Storage（可选）
```

节点机器单独运行 Agent 和内核。开发和测试使用 Docker Compose，生产环境可以先使用单机或少量虚拟机，再迁移到 Kubernetes。

### 12.2 高可用演进

1. API 多实例，前面使用负载均衡。
2. Worker 使用 Redis Streams 或等价的可靠队列，并支持确认、重试和幂等执行。
3. PostgreSQL 使用主从、备份和定期恢复演练。
4. Redis 根据可靠性要求选择哨兵或集群。
5. 订阅接口使用缓存和限流，避免被单个令牌拖垮。
6. 流量明细按时间分区或归档，避免主表无限增长。

### 12.3 可观测性

必须提供：

- API 请求延迟、错误率和状态码分布。
- 数据库连接池、慢查询和事务失败。
- Redis 命中率、队列长度和任务失败。
- Agent 在线率、心跳延迟、配置发布成功率。
- 内核进程状态、CPU、内存、磁盘和重载次数。
- 流量上报延迟和重复上报数量。
- 结构化日志和全链路 Request ID。

## 14. 分阶段实施路线

### M0：需求和协议冻结

交付物：

- 产品边界和角色权限矩阵。
- 领域模型和数据库草图。
- OpenAPI 初版。
- Agent gRPC 协议初版。
- 统一配置模型。
- 威胁模型和密钥管理方案。
- sing-box 目标版本矩阵。
- Agent 出站连接、证书信任根、密钥轮换和吊销流程。
- 配置签名 envelope、canonical bytes、防回放和 generation/CAS 规则。
- 用量接收凭证、幂等、重放和结算边界。

验收标准：核心实体、状态转换、权限边界和配置发布流程都能被评审。

### M1：最小可用版本

范围：

- 用户和管理员登录。
- 套餐、订阅和到期时间。
- 节点注册、心跳和状态展示。
- sing-box 基础配置生成。
- 订阅链接生成。
- Rust Agent 本地启动和重载内核。
- 基础流量上报。

验收标准：从创建用户、创建节点到生成配置并在节点加载成功，流程可以完整闭环。

### M2：可靠性和安全

范围：

- 配置签名、版本和回滚。
- mTLS 或短期 Agent Token。
- RBAC 和审计日志。
- Redis 缓存和异步 Worker。
- 流量上报幂等和断线重试。
- 监控、告警和备份。

验收标准：节点断网、配置错误、重复上报和凭证撤销场景均能恢复或被拒绝。

### M3：商业能力

范围：

- 订单、支付 Provider 接口。
- 优惠码和续费。
- 通知系统。
- 到期、超额和封禁策略。
- 代理商或多租户能力。

验收标准：订单状态、支付回调、订阅生效和额度变化可以审计和重放验证。

### M4：多内核和规模化

范围：

- Xray 或其他内核 Adapter。
- 多地域节点和节点调度。
- 多实例 API 和 Worker。
- 高级统计和归档。
- Agent 灰度升级。

验收标准：新增内核只需要实现适配器和兼容测试，不修改用户、订阅和计费核心逻辑。

## 15. 关键风险与应对

| 风险 | 影响 | 应对方案 |
|---|---|---|
| 内核配置频繁变化 | 配置发布失败 | 版本矩阵、golden tests、原生校验和自动回滚 |
| 流量统计不一致 | 额度和账单错误 | 时间桶、幂等键、补偿任务和账务审计 |
| 节点凭证泄露 | 节点被控制 | 短期凭证、mTLS、轮换、最小权限和撤销 |
| 订阅令牌泄露 | 用户配置被读取 | 独立令牌、轮换、限流、访问审计和可选过期 |
| Agent 升级失败 | 节点离线 | 签名包、双版本、健康检查和自动回滚 |
| 数据库增长过快 | 查询和备份变慢 | 流量分区、汇总表、归档和保留周期 |
| Rust 业务迭代成本高 | 交付速度下降 | 共享领域 crate、清晰边界、统一错误模型和自动化测试 |

## 16. 开始开发前需要冻结的决策

1. 首期是单租户还是预留多租户并只启用一个租户。
2. 首期只支持 sing-box，还是同时支持 Xray。
3. 是否首期包含支付，还是先使用人工开通。
4. 目标节点系统和架构，例如 Linux x86_64、Linux ARM64。
5. 预计的用户数、节点数和日流量规模。
6. 订阅输出格式：sing-box JSON、Clash Meta、通用链接或组合输出。
7. Agent 是否自动更新，以及升级包由谁签名。
8. 数据保留周期、备份位置和灾备目标。
9. 是否需要代理商、分销和多级权限。
10. 团队的 Rust 生产经验、首个可用版本的时间目标，以及是否接受 Rust 依赖和编译维护成本。

## 17. MVP 完成定义

满足以下条件才认为第一版完成：

- 前端和后端独立构建、独立部署。
- 管理员可以创建用户、套餐和节点。
- Agent 可以安全注册、心跳和拉取期望配置。
- 控制面可以生成经过校验的 sing-box 配置。
- Agent 可以校验、加载、重载和回滚配置。

## 18. 最终技术决策

本项目推荐采用 Rust 作为控制面和节点 Agent 的主要语言，Vue 3 + TypeScript 作为前端，PostgreSQL 作为事实数据库，Redis 作为缓存和任务基础设施。

架构上采用“前后端分离 + 控制面与数据面解耦 + 模块化单体起步”。配置使用统一内部模型和内核适配器生成，Agent 使用签名配置和最小权限执行。首期聚焦 sing-box 的稳定闭环，在兼容性、配置回滚和流量统计可靠后再扩展其他内核与商业能力。
